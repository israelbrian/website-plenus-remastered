# Especificação de Integração API: Site Principal (website-plenus-remastered)

Este documento define a arquitetura, as premissas técnicas e a modelagem da integração entre a API Serverless e o **Front-end do Site Principal (público)** de clientes da Plenus Planejados.

---

## 🏛️ Diretrizes de Arquitetura (Fail-Safe & Zero-Cost)

Para garantir velocidade de carregamento excepcional, responsividade instantânea na navegação e custos operacionais nulos na infraestrutura da Cloudflare, adotamos os seguintes padrões:

1. **Recuperação Monolítica em Cache Edge:** A listagem completa de produtos (`GET /produtos`) e categorias (`GET /categorias`) será requisitada pelo front-end com uma regra rígida de revalidação de **15 dias** (`revalidate: 1296000`). 
2. **Filtragem em Memória (Client-Side / Build-Side):** Para evitar requisições desnecessárias ao banco de dados D1 em cliques de filtros, buscas textuais por caractere (que causariam latência de rede) ou durante o processo de pré-renderização estática (SSG), todas as operações secundárias de busca e filtragem ocorrerão localmente sobre o array retornado da API.
3. **Unificação dos Modelos de Dados:** O back-end foi mapeado para retornar chaves idênticas às esperadas pelo front-end (`categoriaSlug`, `imagemPrincipal` e parsing automático do JSON string do SQLite para array de imagens), eliminando a necessidade de mapeadores complexos.

---

## ⚖️ Centralização de Consultas em `products.ts` (Prós e Contras)

As consultas externas e a lógica de dados estão centralizadas no arquivo de serviço `src/lib/products.ts`.

### Pontos Positivos (Vantagens)
* **Single Source of Truth (Fonte Única de Verdade):** Caso a URL da API ou o tempo de revalidação do cache mude, a alteração é feita em apenas uma linha no arquivo `products.ts`, sem impactar os componentes visuais.
* **Encapsulamento de Regras de Cache:** As diretivas específicas do Next.js (como `{ next: { revalidate: X } }`) e o tratamento de cabeçalhos de requisição HTTP ficam isolados na camada de dados, mantendo os componentes visuais limpos e focados apenas em renderização de interface.
* **Componentes de UI mais Limpos:** Os componentes React apenas chamam `await getAllProducts()` ou `await getProductById(id)` sem precisar gerenciar blocos `try/catch`, tratamento de erros de conexão ou conversões de tipos JSON.

### Pontos Negativos (Desvantagens)
* **Abstração Adicional (Indireção):** Desenvolvedores precisam navegar até o arquivo `products.ts` para entender de qual endpoint a informação está vindo e como está estruturada, adicionando um pequeno atrito cognitivo.

* **Controle de Cache Menos Granular:** Se um componente específico na tela precisar de um tempo de cache diferente (ex: revalidar a cada 5 minutos em vez de 15 dias), isso se torna mais difícil de gerenciar através de uma única chamada estática centralizada, exigindo passagem de parâmetros adicionais de configuração.

---

## 🔒 Configuração de Segurança (x-api-key & Variáveis de Ambiente)

Para que o site principal consiga ler as rotas GET protegidas, a chave de API deve ser injetada no cabeçalho de todas as requisições HTTP (`x-api-key`).

### 1. Injeção no Código (`src/lib/products.ts`)
O cliente HTTP do Next.js lê a chave a partir de uma variável de ambiente privada e a insere nos cabeçalhos:
```typescript
const API_KEY = process.env.INTERNAL_API_KEY || '';
// ...
headers: {
  'x-api-key': API_KEY
}
```

### 2. Configuração no Ambiente Local (Dev)
Adicione a chave no arquivo `.env.local` do projeto `website-plenus-remastered` (este arquivo é ignorado pelo Git e não deve ser commitado):
```env
INTERNAL_API_KEY="mesmo-token-definido-no-backend"
```

### 3. Configuração no Ambiente de Produção (Cloudflare Pages)
No painel da Cloudflare do seu site principal:
1. Vá em **Pages** > Seu projeto do site principal > **Settings** > **Environment Variables**.
2. Adicione a variável `INTERNAL_API_KEY` com o valor da sua senha robusta nos campos **Production** e **Preview**.
3. Realize um novo deploy do site para que o Next.js passe a ler essa variável no Edge.

---

## 🔍 Detalhamento das Funções & Mecânica de Build (SSG)

### 1. `getProductById(id)` e `getProductByCategoryAndId(categoria, id)`
Estas funções são executadas de forma assíncrona nas seguintes circunstâncias:
* **Fase de Build (Static Site Generation - SSG):** No Next.js, as rotas dinâmicas como `/produtos/[categoria]/[id]` são pré-renderizadas no servidor durante a build para gerar páginas HTML estáticas de alto desempenho e excelente indexação SEO.
* **Geração de Metadados Dinâmicos (`generateMetadata`):** O Next.js dispara esta função para obter o `nome` e a `descricao` do produto e injetá-los nas tags `<title>` e `<meta>` do HTML (SEO e OpenGraph).
* **Renderização do Servidor (RSC):** Quando o cliente acessa a página após a expiração do cache de 15 dias, a função roda no Edge da Cloudflare para remontar a página.

#### 💡 Justificativa da Abordagem de Filtro em Memória no Build
Embora Next.js faça a geração estática por ID de produto, a função `getProductById` **não faz uma chamada HTTP individual por ID** à rota `/produtos/:id`. Em vez disso, ela consome a listagem monolítica do `getAllProducts()` e filtra os IDs localmente em memória. 

Esta escolha baseia-se nos seguintes pilares técnicos:

| Critério | Consulta por ID (`GET /produtos/:id`) | Filtro em Memória (`GET /produtos` + `.find()`) |
| :--- | :--- | :--- |
| **Requisições no Build** | **51 chamadas** (1 geral + 50 individuais) | **1 chamada** (o Next.js cacheia o fetch monolítico na primeira execução) |
| **Latência do Build** | **Alta** (Adiciona de 5s a 10s ao build esperando conexões sequenciais de rede) | **Irrelevante** (Apenas a primeira request consome rede; as outras resolvem em < 1ms) |
| **Robustez / Risco** | **Alto** (Se uma única request sofrer timeout ou rate-limit, o build inteiro quebra) | **Nulo** (Se a primeira requisição ao catálogo geral passar, 100% das páginas buildam com segurança) |
| **Consistência Atômica** | **Baixa** (Se o banco for atualizado no meio do build, as páginas ficarão inconsistentes) | **Máxima** (Todo o build é gerado sobre o mesmo snapshot de dados, garantindo paridade total) |

## 🛠️ Especificação do Código (`src/lib/products.ts`)

```typescript
import { Product, Category } from '@/types';

const API_URL = process.env.NEXT_PUBLIC_API_URL || 'http://localhost:8787';

// ⏱️ Configuração de cache de 15 dias (fácil manutenção)
export const CACHE_REVALIDATION_TIME = 1296000;

// 🔒 Chave privada do servidor para ler as rotas GET autenticadas
const API_KEY = process.env.INTERNAL_API_KEY || '';

async function fetchAPI<T>(path: string, fallbackValue: T): Promise<T> {
  try {
    const res = await fetch(`${API_URL}${path}`, {
      next: { revalidate: CACHE_REVALIDATION_TIME },
      headers: {
        'x-api-key': API_KEY,
      },
    });

    if (!res.ok) {
      console.error(`Erro ao conectar na API Plenus: ${res.statusText}`);
      return fallbackValue;
    }
    
    return await res.json();
  } catch (error) {
    console.error(`Falha na rede ao conectar na API Plenus:`, error);
    return fallbackValue; // Evita falhas críticas em builds SSG
  }
}

// 1. API: Listar todos
export async function getAllProducts(): Promise<Product[]> {
  return fetchAPI<Product[]>('/produtos', []);
}

// 2. API: Categorias
export async function getAllCategories(): Promise<Category[]> {
  return fetchAPI<Category[]>('/categorias', []);
}

// 3. Memória: Detalhes
export async function getProductById(id: number): Promise<Product | undefined> {
  const products = await getAllProducts();
  return products.find((p) => p.id === id);
}

// 4. Memória: Filtro por Categoria
export async function getProductsByCategory(categoriaSlug: string): Promise<Product[]> {
  const products = await getAllProducts();
  return products.filter((p) => p.categoriaSlug === categoriaSlug);
}

// 5. Memória: Destaques
export async function getFeaturedProducts(): Promise<Product[]> {
  const products = await getAllProducts();
  return products
    .filter((p) => p.destaque)
    .sort((a, b) => b.relevancia - a.relevancia)
    .slice(0, 3);
}

// 6. Memória: Busca textual
export async function searchProducts(query: string): Promise<Product[]> {
  const lowerQuery = query.toLowerCase();
  const products = await getAllProducts();
  return products.filter(
    (p) =>
      p.nome.toLowerCase().includes(lowerQuery) ||
      p.descricao.toLowerCase().includes(lowerQuery)
  );
}

// 7. Memória: Categoria por Slug
export async function getCategoryBySlug(slug: string): Promise<Category | undefined> {
  const categories = await getAllCategories();
  return categories.find((c) => c.slug === slug);
}

// 8. Memória: Validador de Rota do Detalhe
export async function getProductByCategoryAndId(
  categoria: string,
  id: number
): Promise<Product | undefined> {
  const products = await getAllProducts();
  return products.find((p) => p.categoriaSlug === categoria && p.id === id);
}

export function createProductSlug(id: number, name: string): string {
  const slug = name
    .toLowerCase()
    .normalize('NFD')
    .replace(/[\u0300-\u036f]/g, '')
    .replace(/[^\w\s-]/g, '')
    .replace(/-+/g, '-')
    .trim();

## 🧩 Refatoração de Componentes (Server vs Client Components)

A integração com a API introduziu a necessidade de consumir uma variável de ambiente privada (`INTERNAL_API_KEY`). Por regras rígidas de segurança, o **Next.js jamais expõe variáveis privadas para o navegador do cliente**. 

Se tentássemos consumir a função `getAllProducts()` diretamente de dentro de um componente marcado com `'use client'` (como o Catálogo ou o Carrossel), a requisição ao servidor Hono falharia (Retornando `401 Unauthorized`), pois a chave chegaria vazia. 

Para resolver isso de forma segura e performática, a arquitetura de **Server-Side Fetching (Prop Drilling)** foi adotada:

### 1. Busca Segura no Servidor (Server Components)
Os arquivos `app/page.tsx` (Home) e `app/produtos/page.tsx` (Catálogo) operam 100% no servidor (Node.js). Eles são os responsáveis por executar as funções assíncronas (`await getFeaturedProducts()` e `await getAllProducts()`). Como estão no servidor, eles conseguem acessar a chave secreta e bater na API da Cloudflare de forma autenticada e invisível ao usuário final.

### 2. Injeção Visual no Cliente (Client Components)
Componentes interativos (marcados com `'use client'`) como o `FeaturedProducts.tsx`, `CategorySidebar.tsx` e `ProductsPageClient.tsx` **não fazem mais requisições à internet**.
Em vez disso, a página principal (que está no servidor) "passa" os dados obtidos diretamente para esses componentes visuais através de **Propriedades (Props)**.

#### Impactos e Vantagens da Refatoração:
- **Segurança Máxima:** O token `x-api-key` nunca sai do servidor. Hackers não podem ver a senha analisando os arquivos JS no navegador.
- **Performance / Zero Latência:** Os componentes visuais não precisam exibir bolinhas de *Loading* ou *Spinners* esperando a API responder, pois o site já chega renderizado com os produtos injetados.
- **UX em Tempo Real:** No `ProductsPageClient.tsx`, os filtros (por categoria e busca) foram refatorados para atuar diretamente sobre o array de produtos carregado inicialmente usando funções JS puras (`.filter()`, `.includes()`). O resultado são filtros que respondem na mesma fração de segundo em que o cliente digita no teclado, sem disparar gargalos na rede.
